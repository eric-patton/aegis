# Terminal UI Tech Stack for Aegis

Research pass covering TUI framework choices for a rich, polished terminal RPG, plus save game architecture and deterministic RNG practices for a mostly procedural world. Scope: C#/.NET, Rust, Python, TypeScript/Node, evaluated on rendering, widgets, input, color/Unicode support, shipping, testability, and maintenance.

## 1. Overview of the stacks

| Stack | Core libs | Rendering model | Maturity for panels/menus/logs |
|---|---|---|---|
| C#/.NET | Terminal.Gui v2, Spectre.Console | Terminal.Gui: retained-mode widget tree with damage-region redraw. Spectre.Console: mostly imperative "render and move on" | Terminal.Gui: high (dialogs, list views, scroll views, tree views). Spectre.Console: low for persistent app UI, high for one-shot pretty output |
| C#/.NET (alt) | SadConsole (MonoGame/SFML host) | GPU-rendered tile grid that *looks* like a terminal | High, but it is a game engine, not a terminal app |
| Rust | ratatui + crossterm | Immediate-mode UI redrawn to a diffed cell buffer each frame | High (widgets: List, Table, Tabs, Paragraph w/ wrap, Gauge, custom widgets are easy) |
| Python | Textual (+ Rich), blessed | Textual: retained-mode widget tree with CSS-like styling and async event loop. blessed: low-level cursor/attribute wrapper, you build everything | Textual: high. blessed: low, it's a building block |
| TypeScript/Node | Ink (React), blessed/neo-blessed | Ink: React reconciler targets a virtual terminal tree, diffed like React DOM. blessed: retained widget tree, imperative | Ink: medium-high if you're fluent in React. blessed: medium but largely unmaintained upstream |

Sources: [Terminal.Gui vs Spectre.Console comparison](https://www.libhunt.com/compare-spectre.console-vs-Terminal.Gui), [Terminal.Gui GitHub](https://github.com/tui-cs/Terminal.Gui), [SadConsole GitHub](https://github.com/Thraka/SadConsole), [ratatui GitHub](https://github.com/ratatui/ratatui), [Ink GitHub](https://github.com/vadimdemedes/ink), [blessed vs ink comparison](https://npm-compare.com/blessed,ink).

### C#/.NET: Terminal.Gui v2 vs Spectre.Console

Terminal.Gui (maintained at `gui-cs`/`tui-cs`, created by Miguel de Icaza) is the dominant .NET TUI framework: 10.7k stars, 1.6M+ NuGet downloads, 199 contributors as of the v2 beta cycle. It follows a classic single-threaded event loop (`Application.Run`) where one loop handles input, layout, and painting, with background work marshaled through `Application.Invoke()`. v2 rebuilt the driver layer with a pure-ANSI cross-platform mouse/keyboard driver, an instance-based application model (no more static-only state, which matters for multiple save slots or a title-screen-to-game transition), and a real layout engine (`Pos`/`Dim` computed properties, similar in spirit to Avalonia). It ships ColorPicker, DatePicker, TreeView, TableView, ScrollView, Dialog, Wizard, and a graph view out of the box. See [Terminal.Gui v2 what's new](https://gui-cs.github.io/Terminal.Gui/docs/newinv2) and the [beta announcement](https://blog.kindel.com/2026/03/05/terminal-gui-still-absurd-now-beta/).

Spectre.Console is excellent for pretty one-shot console output (tables, progress bars, prompts, markup) but is not built around a persistent, redrawable widget tree the way Terminal.Gui is; community discussion (e.g. building a lazygit-style app) consistently lands on Terminal.Gui once you need panels, focus management, and scrolling regions that update independently. [Discussion thread](https://github.com/spectreconsole/spectre.console/discussions/1347). Spectre.Console remains valuable as a *library*, e.g. for its Figlet/markup renderer at the title screen or for CLI tooling (world seed exporter, save inspector) that isn't the full-screen game itself; Terminal.Gui and Spectre.Console can be used side by side for different surfaces of the same product.

### C#/.NET: SadConsole is not a terminal app

SadConsole is, in its own words, "really a giant tile-based game engine" whose object model is conceptually similar to a console app. It requires a rendering host, MonoGame or SFML, and draws a sprite-sheet tileset mapped to ASCII codes onto a GPU surface; there is no real terminal underneath it, no real stdin/stdout, no OS window manager integration, no `ssh`-ability, no screen reader/accessibility passthrough, and no compatibility with terminal multiplexers (tmux/screen) or terminal-based remote play. It buys you pixel-perfect font control, smooth animation, and mouse-pixel precision that ANSI terminals cannot offer, at the cost of everything that makes a "terminal game" actually a terminal game: it can't run over SSH, doesn't respect the user's terminal color scheme/font/opacity preferences, and adds a full 3D graphics dependency (MonoGame or SFML plus their native libs) to what is nominally a text project. [SadConsole README](https://github.com/Thraka/SadConsole/blob/master/README.md). For Aegis specifically, SadConsole should be treated as a *different genre of product* (a "console emulator" game, like Cogmind's custom SDL terminal emulator, see below) rather than a TUI stack; it is the right tool if the goal shifts to "ASCII-styled desktop game," wrong if the goal is "an actual terminal application."

### Rust: ratatui + crossterm

Ratatui (the actively maintained fork of the abandoned `tui-rs`) is immediate-mode: every frame you rebuild the widget tree and call `terminal.draw()`, and ratatui diffs the new cell buffer against the last one, only emitting ANSI writes for changed cells, which is what keeps a well-written ratatui app flicker-free even on slow SSH links. crossterm is the default backend and is genuinely cross-platform (Windows console API + ANSI on Unix) without external C deps. Best practice from the ratatui team: do not call `terminal.draw()` in a tight loop, gate redraws on an event-or-tick loop (~60fps ceiling), and use the `scrolling-regions` feature or synchronized-output escape (`\x1b[?2026h`, widely supported in 2026 terminals) to eliminate the last bit of tearing on resize. [ratatui rendering discussion](https://github.com/ratatui/ratatui/discussions/579), [ratatui docs](https://docs.rs/ratatui/latest/ratatui/). The ecosystem (`awesome-ratatui`) already contains multiple terminal games (Snake, a Space-Invaders clone "Thardians", a WarGames-style sim), evidence the widget/event model comfortably supports game loops, not just dashboards. [awesome-ratatui](https://github.com/ratatui/awesome-ratatui).

### Python: Textual vs blessed

Textual (Textualize) is the only Python option with a real retained widget tree, CSS-like styling, async event loop, reactive attributes, and a proper layout system (docking, grid, scroll containers) comparable to Terminal.Gui's ambitions. It is explicitly used for a [2025 traditional-roguelike tutorial](https://github.com/Drevarr/textual_rl), showing the community already treats it as roguelike-viable. blessed is a low-level cursor/keyboard/attribute wrapper: useful, but you are hand-rolling every panel, scrollback, and redraw strategy yourself, similar in spirit to raw crossterm without ratatui on top.

Caveat: Textualize Limited (the company) dissolved in February 2026 after failing to find a sustainable business model around the framework, but the maintainer confirms Textual continues as community open source, and GitHub issue activity continues into mid-2026. [The future of Textualize](https://textual.textualize.io/blog/2025/05/07/the-future-of-textualize/). This is a real but moderate risk: no company backing means slower response to Python version churn and less roadmap certainty, but the code and API are mature and widely used (Textual apps ship inside many popular CLI tools already), so existing functionality is unlikely to bit-rot quickly.

### TypeScript/Node: Ink vs blessed

Ink brings React's component model and reconciler to the terminal: you write JSX, Ink's Yoga-based flexbox layout positions boxes, and it diffs re-renders the same way React DOM does, which naturally avoids full-screen flicker. It has by far the largest install base (4.1M weekly downloads vs ~1.1k for react-blessed) and is what GitHub Copilot CLI, Claude Code's own CLI-adjacent tools, and other modern dev-tool CLIs are built on, evidence of strong real-world flicker-free redraw behavior at production scale. [Ink GitHub](https://github.com/vadimdemedes/ink). blessed itself is effectively unmaintained; `neo-blessed`/`reblessed` forks exist for compatibility patches only. [blessed vs ink comparison](https://npm-compare.com/blessed,ink). For a game specifically, Ink's component model is a good fit for panel-heavy UI (character sheet, inventory grid, dialogue box, combat log) but Ink was designed for short-lived CLI tools, not long-running full-screen apps; game-loop-style continuous re-rendering and keyboard-driven modal state (e.g., "targeting mode" overlays) are achievable but you are pushing against React idioms that assume mostly-static, mostly-short-lived UIs.

### How other terminal-adjacent games actually structured their renderer

Beyond the framework-level comparison above, several shipped games make concrete, sometimes surprising choices worth internalizing:

- **Cogmind** (Grid Sage Games) does not use libtcod at all; it runs a custom C++ terminal emulator built on SDL 1.2 that mimics what libtcod/BearLibTerminal provide, because the developer wanted tighter control over rendering than the off-the-shelf libraries offered at the time. [Making a Game - Cogmind](https://www.gridsagegames.com/blog/2014/02/making-game/). Lesson for Aegis: a mature off-the-shelf TUI framework is the right default, but be aware that "roll your own renderer" is a well-trodden path once a project's rendering needs (animation timing, custom glyph effects) outgrow a general-purpose widget library, and that decision should be revisited only if a specific concrete need appears, not preemptively.
- **Brogue (Community Edition)** compiles to two interchangeable backends from one codebase: an ncurses terminal renderer (`-t` flag, `curses-platform.c`) and an SDL2 tile renderer (`tiles.c`), selected at build time. [BrogueCE source](https://github.com/tmewett/BrogueCE). This is direct precedent for keeping the simulation/game-logic layer decoupled from the rendering layer behind a thin interface, so a tile-mode presentation could be bolted on later without touching game rules, echoing the SadConsole caveat in section 1.
- **Dungeon Crawl Stone Soup** separates "engine" (the C++ binary that runs the full simulation and renders ASCII to a console) from "presentation": for local play it writes straight to a real terminal; for WebTiles it instead opens a Unix domain socket and streams the visible game state as JSON to a Python/Tornado webserver that a JS client renders, and the same binary supports pure SSH/telnet console play (via `dgamelaunch`) with zero changes to game logic. [Webtiles architecture](https://crawl.develz.org/wordpress/webtiles-architecture), [webserver README](https://github.com/crawl/crawl/blob/master/crawl-ref/source/webserver/README.md). Lesson: designing the simulation to emit "visible state" as data (not directly painting a screen) is what let DCSS support terminal, SSH, and web play from one core without a rewrite; Aegis should keep a similar seam between "what the world state is" and "how it's drawn," even though the initial target is a single local terminal.

## 2. Rendering performance and flicker

All four "serious" options (Terminal.Gui, ratatui, Textual, Ink) share the same underlying trick: **never blast the whole screen every frame**, instead retain a buffer of the previous frame's cells/attributes and only emit escape sequences for the deltas. This is exactly the technique curses/ncurses pioneered decades ago and remains the correct approach in 2026. The frameworks differ in how automatic vs manual this is:

- Terminal.Gui: automatic via its `ConsoleDriver` damage-region tracking; you rarely think about it.
- ratatui: automatic via `Buffer` diffing inside `Terminal::draw`; you must avoid needlessly high redraw rates yourself.
- Textual: automatic; Textual additionally batches DOM-like "reactive" updates within an event loop tick.
- Ink: automatic via the React reconciler, but nested Box re-layouts on every state change can get expensive if the tree is large; Ink apps commonly memoize expensive subtrees.
- Spectre.Console / blessed: manual; you own flicker avoidance, which is fine for short scripts, risky for a persistent 60-panel game UI.

For a turn-based game (not real-time action), redraw rate is not a bottleneck category the way it would be for a real-time renderer: you are redrawing on player input and simulation ticks, not on a frame clock, so all four serious options comfortably clear the bar.

## 3. Keyboard input, color, and Unicode across platforms

Modern Windows Terminal (the default terminal on Windows 10/11 since 2020, and default shell host since 2022) has supported full 24-bit truecolor since build 14931 and has full Unicode/UTF-8 box-drawing support; the same Box Drawing (U+2500-U+257F) and Block Elements (U+2580-U+259F) ranges render consistently across Windows Terminal, iTerm2, GNOME Terminal, Alacritty, and kitty. [Windows Terminal Unicode support](https://www.infoq.com/news/2020/05/windows-terminal/), [box drawing cross-platform support](https://unicodefyi.com/guide/box-drawing-guide/), [true color terminal support gist](https://gist.github.com/kurahaupo/6ce0eaefe5e730841f03cb82b061daa2). The legacy `cmd.exe` console host is the one real hazard: it historically mishandles some Unicode glyph widths and has patchy truecolor support depending on Windows build; Terminal.Gui, crossterm, and Textual all detect and degrade gracefully (ANSI 256-color or 16-color fallback), but you should assume some players will run inside `cmd.exe` or legacy `powershell.exe` consoles rather than Windows Terminal, and test there.

Keyboard handling differences that matter for an RPG (targeting cursors, modifier-chorded hotkeys, vim-like movement keys):
- Terminal.Gui v2's new ANSI input driver reads raw escape sequences cross-platform (no more separate WinPS/Unix code paths), which is the most robust of the four for chorded input (Ctrl/Alt/Shift + arrow, function keys).
- crossterm exposes a clean, cross-platform `KeyEvent` with modifiers and supports the Kitty keyboard protocol for disambiguating key-up/repeat where the terminal supports it, useful for "hold to run" style movement.
- Textual runs on top of a custom parser over stdin plus its own escape-sequence table, generally solid, occasional lag on some raw modifier combos reported in issues.
- Ink relies on Node's readline plus manual escape parsing; modifier-chord support is the weakest of the four out of the box and commonly needs a supplementary keypress library.

## 4. Shipping a self-contained binary to players

This is where the four stacks diverge most sharply for a shrink-wrapped RPG.

- **C#/.NET**: `dotnet publish` supports Native AOT (`PublishAot=true`) producing a genuinely native, self-contained binary with no runtime dependency, or classic self-contained + single-file trimming if AOT's reflection restrictions are a problem. NativeAOT + single-file is not perfectly airtight yet (native satellite libraries can't always be folded into the one file), but for a console-only app with no heavy reflection-based serialization this is close to solved. [Native AOT deployment overview](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/), [single file deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/single-file/overview). You must build per target OS/arch (or use CI runners for each), same constraint every other stack has.
- **Rust**: the cleanest story. `cargo build --release --target x86_64-pc-windows-msvc` etc, statically linked by default on Windows/macOS, and fully static via musl on Linux (`x86_64-unknown-linux-musl`) with zero runtime dependencies. Cross-compiling from one host with `cross` (Docker-based) is well trodden. Smallest, simplest, most "just an .exe" of the four. [Rust cross-compilation](https://medium.com/@codepitbull/cross-compilation-for-rust-and-how-to-reduce-binary-sizes-by-88-269deea50c1b).
- **Python**: PyInstaller or Nuitka both produce single-file executables, but neither cross-compiles: you must build on each target OS (a Windows box for the Windows exe, etc), which means CI matrix builds are mandatory, not optional. Nuitka compiles to C and gets a real speed win (2-4x over CPython) at the cost of much longer build times; PyInstaller is faster to iterate with but ships an embedded interpreter plus bytecode, larger and slightly more fragile against antivirus false-positives. [PyInstaller vs Nuitka](https://sparxeng.com/blog/software/python-standalone-executable-generators-pyinstaller-nuitka-cx-freeze), [Nuitka intro](https://www.infoworld.com/article/2336736/intro-to-nuitka-a-better-way-to-compile-and-distribute-python-applications.html).
- **Node/TypeScript**: Bun's `bun build --compile` bundles source plus the Bun runtime into one binary and explicitly supports `--target` cross-compilation from a single host to Windows/macOS/Linux binaries, the only stack here where you can cross-compile to all three OSes from one machine without emulation or Docker. [Bun single-file executables](https://bun.com/docs/bundler/executables). The catch is Bun is a fast-moving alternate runtime, not upstream Node, so subtle compatibility gaps against packages that assume Node-specific APIs are still possible; verify Ink and its dependency tree run clean under Bun before committing.

## 5. Testability

- **ratatui**: `TestBackend` renders to an in-memory cell buffer with no real terminal, ideal for unit tests, pairs naturally with the `insta` snapshot crate (`assert_snapshot!` on the buffer). For full PTY-level behavior (resize negotiation, real terminal emulator quirks), `ratatui-testlib` spins up a real pseudo-terminal. This is the most complete, most "designed for testing" story of the four. [Testing with insta snapshots](https://ratatui.rs/recipes/testing/snapshots/), [TestBackend docs](https://docs.rs/ratatui/latest/ratatui/backend/struct.TestBackend.html).
- **Textual**: first-party `pytest-textual-snapshot` plugin renders the app to SVG and diffs against a stored snapshot, plus a scriptable `Pilot` object (`app.run_test()`) for simulating keypresses and asserting on widget state, very strong, arguably the best developer-experience of the four for writing behavioral tests against actual rendered output. [pytest-textual-snapshot](https://github.com/Textualize/pytest-textual-snapshot).
- **Terminal.Gui**: testable at the model/view-model layer via normal xUnit/NUnit since views expose their state as plain C# objects, but there is no first-party visual-snapshot tool as polished as the Rust/Python ones; driver-level testing exists but is less turnkey.
- **Ink**: `ink-testing-library` (community, React-Testing-Library-style) lets you render an Ink tree to a string and assert on it; workable, less mature than ratatui's or Textual's official snapshot tooling.

## 6. Save-game architecture for procedural RPGs

Two broad models, and the right answer for Aegis is a hybrid, not a pure pick:

**Full state snapshot** (serialize the entire world/entity graph on save): simple, robust, seek-anywhere (you can load any save instantly without recomputation), but scales with world size. Dwarf Fortress is the canonical cautionary tale: because it snapshots full simulated history (civilizations, sites, populations, events) rather than just a seed, save folders range from a few MB for a short history to multiple GB for a long one, and multi-century worldgen itself can take a very long time to redo if you ever needed to. [DF world generation](https://dwarffortresswiki.org/index.php/World_generation), [DF saved game folder](https://www.dwarffortresswiki.org/index.php/Saved_game_folder). Cataclysm: Dark Days Ahead takes a lighter version of the same approach: per-chunk JSON snapshots of only the map areas the player has actually visited/changed, keeping unvisited world regions purely seed-derived and regenerated on demand rather than ever serialized. [Cataclysm save format](https://discourse.cataclysmdda.org/t/how-world-save-system-really-works/27005).

**Seed + delta/event log** (store the master seed plus a journal of everything that deviated from pure generation, e.g. player actions, quest state, kills, item pickups): far smaller saves, and doubles as a natural mechanism for "replay" and debugging, but is fragile: if any part of the generation algorithm is not perfectly deterministic (float rounding, iteration-order-dependent hashing, engine/version upgrades), replays diverge and old saves silently corrupt. Generic game-replay literature confirms the tradeoff generically: deterministic/input-log replay is dramatically smaller than snapshotting (a naive full-snapshot replay can be ~200MB for 18,000 frames) but can't "seek" to an arbitrary point without recomputing everything before it, and a single non-deterministic operation anywhere in the chain (even one misplaced float) breaks the whole replay. [Developing your own replay system](https://www.gamedeveloper.com/programming/developing-your-own-replay-system).

Caves of Qud's approach is the most directly relevant reference for Aegis's "authored narrative inside a procedural world" pillar: hand-authored lore, a main quest line, and key locations stay fixed across playthroughs, while dungeons, wilderness, and most incidental history are freshly generated per seed, layered together rather than treated as one monolithic procedural blob. Its generation stack leans on Wave Function Collapse for structured layouts (buildings, crypts, lairs) and FastNoise for organic terrain, all seed-driven. [End-to-end procedural generation in Caves of Qud (GDC)](https://media.gdcvault.com/gdc2019/presentations/Grinblat_Jason_End-to-End_Procedural_Generation.pdf), [Caves of Qud procgen overview](https://www.gamedeveloper.com/design/tapping-into-the-potential-of-procedural-generation-in-caves-of-qud). This "seeded generation for the disposable/regenerable parts, real persisted state for the authored/mutated parts" split is the practical middle ground between the two pure models.

Cataclysm: Dark Days Ahead is also a useful reference for the on-disk format itself, not just the regeneration policy: its saves are plain, human-readable JSON per world, one file per character plus per-visited-chunk map data, editable in a text editor for debugging or modding. [Cataclysm modding/JSON docs](https://docs.cataclysmdda.org/JSON/JSON_INFO.html), [savegame editing wiki](https://cddawiki.danmakudan.com/wiki/index.php/Savegame_Editing). For Aegis, a human-readable (JSON or a similarly diffable text format) save format is worth the modest size/parse-speed cost during development: it makes bug reports ("here's my save, the quest state looks wrong") trivially inspectable, and it makes automated regression tests (load save, assert on parsed state) straightforward without a custom binary-format reader.

## 7. Deterministic RNG: splittable, hierarchical seeds

The standard, well-documented failure mode is a single shared PRNG instance consumed by multiple subsystems (terrain, then vegetation, then NPC placement, then loot) in a fixed call order: change *anything* about how much randomness one subsystem consumes (add a new terrain feature that rolls one extra die) and every subsystem generated after it silently shifts to different outputs, even though the "seed" never changed. The standard fix is **seed splitting**: derive one independent child PRNG stream per subsystem by hashing the master seed together with a stable subsystem identifier (e.g. `hash(masterSeed, "terrain")`, `hash(masterSeed, "npc_names")`, `hash(masterSeed, "loot_table")`), so subsystems are mutually order-independent and each can be re-run, tested, or seeded in isolation without perturbing the others.

This generalizes recursively into a **seed tree**: a region's seed is derived from the world seed plus its coordinates, a dungeon inside that region derives its seed from the region seed plus a dungeon index, an individual loot roll inside that dungeon derives from the dungeon seed plus a room index, and so on; as long as each child hash only needs its immediate parent's seed plus a locally stable identifier, you get "regenerate just this one dungeon deterministically" without touching or even loading the rest of the world. SplitMix64 is the standard, fast, well-mixed generator used specifically for this seed-derivation step (not as the main gameplay RNG, though it's fine for that too); PCG additionally supports explicit numbered streams (`set_stream(n)`) as an alternative mechanism for the same goal. [Critiquing PCG's streams](https://www.pcg-random.org/posts/critiquing-pcg-streams.html), [SplitMix64 reference implementation](https://github.com/indiesoftby/defold-splitmix64), [hierarchical seed splitting](https://arxiv.org/pdf/2605.05099).

Practical rules that fall out of this for Aegis:
1. Never let two subsystems share one PRNG instance; every subsystem, and ideally every "regenerable unit" (a dungeon floor, a town, a loot table roll, a combat's crit rolls), gets its own child stream derived by hashing an identifier into the parent seed.
2. Consume randomness in a fixed, engine-version-pinned order within each subsystem; treat any change to that order as a save-breaking change and version-gate it.
3. Never seed any roll from real-world nondeterministic sources (wall-clock time, thread scheduling, dictionary/hash-set iteration order) anywhere in generation code; it is the single most common way "deterministic" procgen silently isn't.
4. Store the identifier scheme itself (how seeds are derived) as part of your save format's versioned contract, since it is exactly as load-bearing as the master seed.

## 8. Pitfalls and failure modes observed across sources

- Treating a full-history-simulation snapshot model (Dwarf-Fortress-style) as free: save sizes and worldgen time both scale with simulated history depth; decide up front how much "history" Aegis actually needs persisted versus regenerable.
- Mixing a single global RNG across subsystems, then "fixing" a bug in one subsystem and unknowingly breaking every save made before the fix because downstream subsystems now consume the shared stream differently.
- Picking SadConsole (or any GPU tile-engine) because it "looks more like the game we want" without registering that it forfeits SSH play, terminal multiplexer support, and the player's own font/theme preferences, all of which are consistent with the "just a well-crafted terminal app" vibe of Aegis's stated inspirations.
- Assuming Ink or blessed's short-CLI-tool-oriented design scales cleanly to a long-running full-screen game loop; both are provably capable in production tools, but expect more custom work for continuous game-loop state than Terminal.Gui/ratatui/Textual, which were designed for persistent apps from the start.
- Under-testing on the legacy Windows `cmd.exe`/`powershell.exe` console hosts because development happens exclusively in Windows Terminal; real players will still launch from shortcuts that open the legacy host.
- Confusing "deterministic today" with "deterministic forever": a compiler/runtime upgrade, a floating-point library update, or even switching build architectures (x86 vs ARM) can change float rounding behavior; keep RNG and generation logic on integer/fixed-point math wherever the algorithm allows it, precisely because Aegis's core promise ("same seed reproducible world," NG+ chaining) depends on long-term bit-for-bit stability.

## 9. Recommendations for Aegis

1. **Build on Rust with ratatui + crossterm as the primary stack.** It has the strongest combination of flicker-free rendering (explicit diffed-buffer model, well documented), the cleanest cross-platform static-binary story of any option here (musl-static Linux, no runtime to bundle, straightforward cross-compilation), and the best first-party testing story (`TestBackend` + `insta` snapshots, `ratatui-testlib` for PTY-level integration tests). For a project with a 10+ year ambition (infinite NG+, ongoing content), shipping a genuinely dependency-free binary to players on Windows/macOS/Linux without worrying about a runtime version matters a lot, and Rust's determinism (explicit integer types, no hidden float-vs-double platform quirks, no GC pauses that could ever interact with save-timing) pairs naturally with the seed-tree determinism requirement in section 7.
2. **Runner-up: C#/.NET with Terminal.Gui v2.** If the team's existing skills or tooling lean C# (and the CLAUDE.md context here suggests familiarity with .NET and Godot tooling), Terminal.Gui v2 is a fully mature, actively developed (beta as of mid-2026, high bar for API stability going forward), widget-rich alternative with the second-best story here: NativeAOT gets you close to a true self-contained binary, and the widget catalog (TreeView, TableView, ScrollView, Dialog) directly covers panels/menus/scrolling logs out of the box with less custom-widget work than ratatui requires. Pair it with Spectre.Console for the title screen, CLI-side tooling (save inspector, seed export), and any place you want pretty one-shot markup rather than persistent widgets.
3. **Do not use SadConsole**, or any GPU console-emulator, for the main game. It is a legitimate engine for a different kind of product (an "ASCII-look desktop game"), but it forfeits the actual-terminal properties (SSH, multiplexer, user theme/font respect) that make this project a TUI game rather than a GPU game with a retro skin. If a tile/graphics mode is ever wanted as a secondary presentation layer, treat it as a wholly separate renderer bolted on later, not the foundation.
4. **Adopt a hybrid save architecture, not a pure model**: persist a versioned "world seed contract" (master seed plus the exact generation-algorithm version) for everything regenerable (unvisited dungeons, wilderness, most NPC flavor content), and persist real delta state only for what has been authored or mutated (main quest progress, named NPCs' relationship/dialogue state, player inventory/stats, anything the player has directly touched), following the Caves-of-Qud "fixed lore skeleton plus generated flesh" split and the Cataclysm-DDA "only serialize visited chunks" pattern. This keeps saves small, keeps NG+ world regeneration honest (a fresh seed truly means a fresh world), and avoids the Dwarf-Fortress trap of save size scaling unboundedly with simulated history.
5. **Implement RNG as an explicit seed tree from day one**: one master seed per character/world, hashed with stable string identifiers (region coordinates, dungeon index, subsystem name, quest id) to derive every child stream via SplitMix64 or an equivalent well-mixed hash, never a single shared global `Random`. Version-gate the identifier scheme and the consumption order per subsystem in the save format so future balance patches can't silently corrupt old seeds; this is the single highest-leverage decision for "no two playthroughs the same" plus "infinite reproducible NG+" both working correctly for years.
6. **Test rendering with the framework's native snapshot tooling from the start** (ratatui's `insta` + `TestBackend`, or Terminal.Gui's xUnit-based view testing), and separately unit-test the RNG/seed-tree and save/load round-trip logic with no terminal dependency at all; keeping "is the UI drawn correctly" and "is the simulation deterministic" as two independently testable layers is what will keep both testable as the widget count and world complexity grow.
